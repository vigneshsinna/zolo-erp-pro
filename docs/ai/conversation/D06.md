# D06 — Conversational dependent masters

Stacked on D05 (`dae2d2f`). The focused warehouse conversation initially returned `needs_input` instead of `master_needs_input` (1 failure / 4 assertions).

New master requests check existing eligible records through the existing directory and present duplicates first. Explicit requests then use `DependentMasterOrchestrator` spawn/preview and its separate signed approval/command flow. Named chat details persist in the existing `dependent_masters_json`, survive reload and prepare a master proposal only when its schema is complete. Product conversations require explicit SKU, eligible UOM, tax category and HSN; they do not accept the legacy engine's unrelated product defaults. Existing manual master UI remains available.

The existing orchestrator now checks the parent branch/FY/status and linked field/proposal before approval, reuses completed execution receipts on retry, and returns `master_created_parent_pending` if resumption fails after creation. The created master is retained. A subsequent retry recovers its receipt and resumes the same parent. Successful resumption returns the parent's remaining question or one existing-engine PO proposal, never an approval of that PO. Already completed resumption does not inject the slot again.
